SH-LAB/02 Network

Stack-up

Six layers between the internet and a service.

Read it like a cross-section of a circuit board. Traffic from the internet stops at the first layer. A request from one of my own devices passes every control on its way to a service, and the last layer filters the lookups that go back out.

Internet My devices
  1. L1 · Edge L1

    Network edge

    No ports are forwarded on the router, so nothing on the Pi answers the open internet. A scan from outside finds nothing to talk to.

    Router · zero port forwards

  2. L2 · Mesh L2

    Private mesh

    Tailscale connects my devices over WireGuard, each with its own key. Tailnet Lock is on, so a new device can’t join until a device I already trust signs it.

    Tailscale · WireGuard · Tailnet Lock

  3. L3 · Access L3

    Service access

    Services listen on localhost. A reverse proxy serves them over HTTPS inside the mesh and renews its own certificates.

    Reverse proxy · automatic TLS

  4. L4 · Firewall L4

    Host firewall

    UFW allow-lists each Docker subnet for only the ports it needs. SSH is accepted over the tailnet and refused from the local network.

    UFW · per-subnet rules

  5. L5 · Segments L5

    Segmentation

    Monitoring, proxy, and application containers sit on separate Docker networks. One compromised container can’t reach unrelated ones.

    Docker bridge networks

  6. L6 · DNS L6

    DNS, on the way out

    Pi-hole filters lookups for every device on the network. Unbound resolves recursively and validates DNSSEC.

    Tested Queried domains with valid and deliberately broken signatures. The resolver rejected the broken ones.

    Pi-hole · Unbound · DNSSEC

SH-LAB/03 Signals

Monitoring

When something breaks quietly, my phone finds out.

Metrics and logs from the host, the containers, and each service flow into one place. Rules decide what counts as broken, and alerts arrive without anyone watching a dashboard.

Sources

  • Host exporterCPU, memory, disk, temperature
  • Container metricsPer-container usage
  • App exportersDNS and service metrics
  • Endpoint probesDoes it answer?
  • LogsHost and containers

Collect

  • PrometheusStores metrics, evaluates alert rules
  • Loki + AlloyShips and indexes logs

Route & view

  • AlertmanagerGroups alerts and routes them
  • GrafanaHost, container, and DNS dashboards

Reach

  • My phonePush notification on failure and recovery

Answering is not the same as working.

Probes ask whether each endpoint responds. A separate rule checks that the metrics I expect are arriving, because an exporter can stay reachable while the data behind it disappears. That happened once.

The alert path is tested too.

I sent a synthetic alert through Alertmanager and confirmed it arrived on my phone. A rule that fires into a broken delivery pipeline protects nothing.

SH-LAB/04 Hardening

Hardening

Every container starts with nothing and asks for what it needs.

The same pattern repeats across my Compose files. It’s applied wherever the image supports it, and exceptions are added back by name.

compose.yamlsanitized excerpt

services:
  exporter:
    image: example/exporter
    user: "1000:1000"             1
    read_only: true               2
    cap_drop: [ALL]               3
    security_opt:
      - no-new-privileges:true    4
    networks: [monitoring]        5
    secrets: [scrape_token]       6
  1. 1

    Unprivileged user

    The process runs under a mapped UID and GID instead of root.

  2. 2

    Read-only root filesystem

    Nothing can rewrite the image at runtime. Paths that must be writable are mounted on purpose.

  3. 3

    No Linux capabilities

    Everything is dropped first. A service that needs one gets it back with an explicit cap_add.

  4. 4

    No privilege escalation

    Processes can’t gain privileges after start, even through setuid binaries.

  5. 5

    One network

    The container joins only the bridge it needs, which keeps lateral movement short.

  6. 6

    Secrets as files

    Tokens are mounted read-only and never written into version-controlled config. Prometheus reads its scrape token from a file.

Reviewed updates. Stateful services are excluded from automatic image updates. Upgrades to anything that holds data get read, backed up, and applied by hand.

Backup automation

Verified

Backups kept missing their destination.

Symptom
Backups finished locally, but their copies often missed the window when the destination device was online.
Fix
Added a scheduled retry job that sends pending archives and skips copies that already exist.
Verification
Compared checksums on both sides, opened selected archives, and added a metric for the last successful transfer. Restore steps for each service live in a runbook.
  1. PackageData and config archived
  2. Store locallyCopy on the Pi
  3. TransferRetries until delivered
  4. VerifyChecksums match

Each stage reports its own last success, so a healthy local backup can’t hide an overdue transfer.
